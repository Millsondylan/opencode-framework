# Row-Level Security (RLS)

## Policy

Every Supabase or Postgres table created or modified during pipeline execution must have Row-Level Security enabled before the migration is committed. Every view on a user-data table must be defined with `security_invoker = true` so that the view inherits the RLS context of the calling user rather than the view owner. See rule 11 for the view-specific enforcement details.

Scope:

1. Every `CREATE TABLE` statement in any migration file under `supabase/migrations/`, `db/migrations/`, or equivalent.
2. Every `ALTER TABLE ADD COLUMN` that introduces columns containing user-identifiable data (`user_id`, `org_id`, `tenant_id`, `email`, `phone`, etc.).
3. Every `CREATE VIEW` or `CREATE MATERIALIZED VIEW` that exposes rows from an RLS-protected table.
4. Every table created via Supabase Studio or the Supabase CLI.
5. Every table created by an ORM migration (Prisma, Drizzle, TypeORM, SQLAlchemy).

A migration that lacks `ENABLE ROW LEVEL SECURITY` on a user-data table must not merge into the main branch.

## Rationale

1. Multi-tenant isolation. When RLS is disabled, any authenticated client with PostgREST access can read every row from every tenant. A single bug in the client-side filter exposes every customer's data.
2. Defense in depth. Application-layer authorization in the Next.js route handler, the Flutter repository, or the Node service is insufficient. A CVE in the backend framework, a misconfigured middleware, or an accidental public route handler must not bypass authorization. RLS moves the enforcement into the database engine where it cannot be accidentally skipped.
3. Prevents privilege escalation via PostgREST. Supabase exposes every table over a REST API generated by PostgREST. Without RLS, any client holding the `anon` or `authenticated` role can `SELECT`, `INSERT`, `UPDATE`, or `DELETE` against any table. With RLS, the database rejects the operation before it reaches the application.
4. Auditable by default. Policies are SQL objects visible in `pg_policies`. Security reviews can enumerate every access path without reading application code.
5. Survives backup and restore. RLS policies migrate with the schema. Disabling RLS temporarily for a backfill and forgetting to re-enable it is a common root cause of data breaches.

## Enable Syntax

```sql
ALTER TABLE public.<t> ENABLE ROW LEVEL SECURITY;
```

For every user-data table, run this statement immediately after `CREATE TABLE` in the same migration. Example:

```sql
CREATE TABLE public.accounts (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  balance    numeric(18, 2) NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE public.accounts ENABLE ROW LEVEL SECURITY;
```

To enforce RLS even for the table owner (recommended in multi-tenant schemas), also run:

```sql
ALTER TABLE public.accounts FORCE ROW LEVEL SECURITY;
```

Without `FORCE`, the table owner bypasses all policies. In Supabase the owner role is `postgres`, which is the role that signed backend service-role tokens effectively operate as. If your backend uses the `service_role` key for privileged reads, you do not need `FORCE` (the service bypass is intentional). If every access path goes through per-user JWTs, prefer `FORCE`.

## Required Policies

Every RLS-enabled table must declare at least one policy for each operation the table supports. If a table is append-only (no updates, no deletes), omit the policies for unused operations rather than adding a permissive `USING (true)` rule.

Minimum policy set:

```sql
CREATE POLICY "accounts_select_owner"
  ON public.accounts
  FOR SELECT
  TO authenticated
  USING (auth.uid() = user_id);

CREATE POLICY "accounts_insert_owner"
  ON public.accounts
  FOR INSERT
  TO authenticated
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "accounts_update_owner"
  ON public.accounts
  FOR UPDATE
  TO authenticated
  USING (auth.uid() = user_id)
  WITH CHECK (auth.uid() = user_id);

CREATE POLICY "accounts_delete_owner"
  ON public.accounts
  FOR DELETE
  TO authenticated
  USING (auth.uid() = user_id);
```

Rules:

1. Every policy names the operation explicitly (`FOR SELECT`, `FOR INSERT`, `FOR UPDATE`, `FOR DELETE`). Never use `FOR ALL` on a user-data table, because a single bug in the predicate then affects every code path.
2. Every policy names the role (`TO authenticated`, `TO anon`). Never omit `TO`, because the default is `PUBLIC` which includes roles you may not have considered.
3. `USING` controls which rows are visible for `SELECT`, `UPDATE`, and `DELETE`. `WITH CHECK` controls which rows are acceptable for `INSERT` and `UPDATE`. Both must be specified on `UPDATE` policies or a user can change a row they cannot see.
4. Policy names are unique per table, not globally. Use a `<table>_<operation>_<actor>` convention.

## Common Patterns

### Owner-based

The most common pattern: the row has a `user_id` column equal to the JWT subject.

```sql
CREATE POLICY "notes_select_owner"
  ON public.notes
  FOR SELECT
  TO authenticated
  USING (auth.uid() = user_id);
```

### Role-based

Use when an admin role must see every row but regular users see only their own.

```sql
CREATE POLICY "audit_log_select_admin"
  ON public.audit_log
  FOR SELECT
  TO authenticated
  USING (
    (auth.jwt() ->> 'role') = 'admin'
    OR user_id = auth.uid()
  );
```

Store the role claim in the JWT app_metadata, not user_metadata. user_metadata is client-writable in Supabase and therefore untrusted.

### Organisation-based (multi-tenant)

Use when rows belong to an organisation and users belong to organisations through a membership table.

```sql
CREATE POLICY "projects_select_member"
  ON public.projects
  FOR SELECT
  TO authenticated
  USING (
    EXISTS (
      SELECT 1
      FROM public.org_members om
      WHERE om.org_id = projects.org_id
        AND om.user_id = auth.uid()
    )
  );
```

Index the join columns on the membership table (`org_members(user_id, org_id)`) because this predicate runs on every query.

### Public-read, auth-write

Use for catalogs, blog posts, or any content that all visitors may view but only authors may modify.

```sql
CREATE POLICY "articles_select_public"
  ON public.articles
  FOR SELECT
  TO anon, authenticated
  USING (status = 'published');

CREATE POLICY "articles_insert_owner"
  ON public.articles
  FOR INSERT
  TO authenticated
  WITH CHECK (auth.uid() = author_id);

CREATE POLICY "articles_update_owner"
  ON public.articles
  FOR UPDATE
  TO authenticated
  USING (auth.uid() = author_id)
  WITH CHECK (auth.uid() = author_id);
```

The `SELECT` policy restricts visibility to `status = 'published'`, so drafts remain private even though the role list includes `anon`.

### Service-role bypass

The Supabase `service_role` key bypasses RLS by design. Any backend path that must read or write on behalf of a user should still use the user's JWT so that RLS applies, not the service-role key. Reserve the service-role key for admin-only background jobs (webhooks, nightly aggregations) and never expose it to the client bundle.

## Forbidden

1. `ALTER TABLE <t> DISABLE ROW LEVEL SECURITY` in any committed migration without a documented exception (see Exception Process below). This is the single most common cause of data leaks in Supabase projects.
2. `CREATE POLICY ... USING (true)` on any user-data table. A permissive policy is equivalent to disabled RLS and must be rejected in review.
3. `CREATE POLICY` on a view. Views do not support RLS policies directly. Use `security_invoker = true` on the view so that the underlying table's policies apply to the caller. See rule 11.
4. Writing policies that reference `current_user`, `session_user`, or `CURRENT_ROLE`. These resolve to the database role, not the application user, and in Supabase they are always the same value (`authenticated` or `anon`). Use `auth.uid()` and `auth.jwt()` instead.
5. Using `SECURITY DEFINER` functions to bypass RLS from application code. If a function must bypass RLS for a specific reason, it requires the same exception process as disabling RLS.
6. Granting `SELECT`, `INSERT`, `UPDATE`, or `DELETE` on user-data tables to `PUBLIC`. Grant only to `authenticated` and, where appropriate, `anon`.

## Verification

`pre-flight-checker` runs the following query against the target database before allowing any build-agent to proceed with a migration:

```sql
SELECT
  n.nspname  AS schema,
  c.relname  AS table,
  c.relrowsecurity,
  c.relforcerowsecurity
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND n.nspname NOT IN ('pg_catalog', 'information_schema', 'pg_toast')
  AND n.nspname NOT LIKE 'pg_temp_%'
  AND n.nspname NOT LIKE 'pg_toast_temp_%'
  AND c.relname NOT IN ('schema_migrations', 'ar_internal_metadata')
ORDER BY n.nspname, c.relname;
```

The check fails the pre-flight stage if any row in the result set has `relrowsecurity = false` for a table in the `public` schema or any application-owned schema. The failure message lists the offending tables so the orchestrator can route to the appropriate build agent for remediation.

Additional verification steps:

1. `pg_policies` enumeration: confirm that every RLS-enabled table has at least one policy per operation that the application performs.
2. Policy coverage test: for each table, run a representative query as the `authenticated` role with a synthetic JWT and confirm the returned row set matches the expected owner filter.
3. Negative test: run the same query with a different user's JWT and confirm zero rows are returned.
4. Review the diff of every migration touching `supabase/migrations/` for any `DISABLE ROW LEVEL SECURITY` string before merge.

## Exception Process

RLS may be temporarily disabled only for a data backfill, a schema migration that rewrites ownership columns, or a one-time import. Every exception requires:

1. A decision record at `docs/decisions/NNNN-rls-disable-<table>.md` that states: the table, the reason, the start time, the expected duration, the operator's identity, and the rollback plan.
2. A paired commit that disables RLS and a follow-up commit that re-enables it. Both commits reference the decision record by filename.
3. A CI gate that asserts RLS is enabled on the target table before the main branch deployment runs. If the re-enable commit is missing, deployment halts.
4. A post-mortem entry if the exception window exceeded four hours.

Forbidden shortcuts:

1. Disabling RLS in production via the Supabase dashboard. The change is not captured by migrations and cannot be audited.
2. Shipping a release with RLS disabled "temporarily" and intending to re-enable it later. The follow-up commit never lands. Pair the disable and re-enable in the same pull request.
3. Working around RLS by issuing the backfill from a `service_role` connection without disabling RLS. This is acceptable only when the decision record documents that the `service_role` key was used and the operator's identity is recorded.
